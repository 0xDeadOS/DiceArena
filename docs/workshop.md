# Инвентарь, шесть сфер и PS: контракт этапа 3

Состояние реализации v2.0: операции над **существующим принадлежащим игроку** кубиком. Нельзя передать в запросе пользователя/чат, готовые грани, свойства, цену, PS или результат RNG.

Диапазоны случайной грани, веса тиров, выход пыли и коэффициенты пассивного EV ниже — **явно выбранные временные параметры** этого инкремента. Это не финальный баланс, не чистый DPS и не скрытые множители редкости. Боевые эффекты и таблица 15 свойств описаны в [combat.md](combat.md).

## Предмет, слоты и защита

- Один профиль `(Telegram user, room)`, максимум **12 предметов**. Сферы/пыль не занимают слоты. В БД лимит контролирует trigger при INSERT/смене владельца, сериализующий операции через целевой member.
- Экипируется только собственный поддерживаемый кубик. Один источник истины — `RoomMember.equippedDieId`; `isEquipped` в DTO вычисляется.
- Защита `isLocked` блокирует все шесть сфер и распыление. Экипировать защищённый кубик можно. Повтор уже установленного equip/lock state с новым ключом отклоняется без расхода/новой ревизии.
- **Нельзя распылить:** стартовый, защищённый, экипированный, используемый снимком незавершённого похода или UNIQUE-кубик. Для UNIQUE пока недоступны также equip/craft.
- Распыление безвозвратно удаляет предмет. Временный выход: NORMAL → **1**, MAGIC → **3**, RARE → **6** пыли. Качество/ilvl/аффиксы не добавляют пыль. Других наград нет.
- Крафт/экипировка в активном походе разрешены, но не меняют его снимок. Параметры применятся при старте следующего похода. Предмет старого снимка остаётся защищённым от распыления, даже если в руке уже другой.
- Крафт не создаёт новый предмет: сохраняются ID, owner, база, ilvl, `isStarter`, `isLocked`, `masterCrafted`. Качество/грани сохраняются, кроме явно изменяемых соответствующей сферой.

## Шесть сфер

Каждая успешная операция расходует **ровно одну соответствующую сферу**, без gold/dust fee. Подтверждение обязательно для **всех** сфер; разрушительные случаи дополнительно отмечены. Недопустимое действие/нехватка валюты не расходуют сферу. Случайное совпадение с прежним содержимым — допустимый оплаченный результат, не повод бесплатного переброса.

| Сфера                    | Допустимый предмет              | Результат                                                              | Что теряется                                    |
| ------------------------ | ------------------------------- | ---------------------------------------------------------------------- | ----------------------------------------------- |
| Закалка `TEMPERING`      | NORMAL/MAGIC/RARE, качество <20 | `quality = min(20, quality + 5)`, без RNG                              | Ничего; округление может оставить PS прежним    |
| Гранение `FACETING`      | NORMAL/MAGIC/RARE               | Одна из шести граней получает новое действие и базовое значение        | Прежняя выбранная грань                         |
| Отливка `CASTING`        | NORMAL или MAGIC                | MAGIC, **новый** набор 1–2 свойств                                     | Старые аффиксы, если был MAGIC                  |
| Возвышение `ASCENDANCE`  | Только MAGIC                    | RARE, всего 3–4 свойства; прежние ID/kind/tier/value сохраняются точно | Ничего                                          |
| Перерождение `RESHAPING` | Только RARE                     | **Новый** набор 3–4 свойств, редкость RARE                             | Все прежние аффиксы                             |
| Очищение `CLEANSING`     | MAGIC или RARE                  | NORMAL, 0 аффиксов                                                     | Все аффиксы и редкость; качество/грани остаются |

### Случайное гранение

Сервер равномерно выбирает одну из шести граней, затем одно из четырёх действий, затем целое базовое значение из замкнутого диапазона. Старая грань не исключается. Выбор конкретной грани/действия за пыль — будущая **точечная огранка**, не эта сфера.

`step = floor((ilvl − 1) / 5)`, ilvl 1–50:

| Действие | Временный диапазон                      |
| -------- | --------------------------------------- |
| STRIKE   | `4 + step … 7 + step`                   |
| GUARD    | `5 + step … 8 + step`                   |
| PIERCE   | `3 + step … 6 + step`                   |
| HEAL     | `2 + floor(step/2) … 4 + floor(step/2)` |

### Генерация аффиксов

1. Число свойств: 1 или 2 для MAGIC, 3 или 4 для RARE — равновероятно.
2. ID выбирается по весам каталога из ещё не взятых свойств, которые не превышают лимит **2 PREFIX + 2 SUFFIX**. Вес каждый раз нормализуется по оставшемуся допустимому пулу. Не обязательно по одному префиксу/суффиксу на MAGIC.
3. T1 доступен с ilvl 1, T2 с 10, T3 с 20. Временные веса **70 / 25 / 5** нормализуются по доступным тирам: на ilvl 10 это 70/95 и 25/95, а не 70%/25% с потерянными 5%.
4. Значение — равномерное целое в диапазоне выбранного тира; fixed range не требует draw.
5. В Возвышении прежние свойства не перебрасываются и исключены из пула новых. Итог повторно проходит `combatDieSchema`.

Клиент не может получить бесплатный preview случайного результата. Только новый успешный подтверждённый command выполняет крафт; replay возвращает старый результат.

## Эффективные грани и автоматический PS

Модель: **`ETV_PASSIVE_V1`**, горизонт **H = 6 ходов**. `evaluateDiePowerScore` использует те же `facePlay`/округление, что и бой. Модель не симулирует конкретного врага, политику игрока, overkill/overheal или полную длительность боя.

Для каждой грани i:

```text
v_i = max(0, floor((base_i × (1 + quality/100) + flat_i) × (1 + percent_i/100)))
```

В flat/percent уже включены имплисит базы и P1/P2/P3/P4/P5/P7. Значение зависит от номера/действия грани, а не от редкости. GUI получает `effectiveFaces` с сервера и отдельно показывает сохранённые базовые `faces`.

```text
opposite(i) = 7 − i
synergy_i = 1.1, если действия противоположных граней различаются, иначе 1
faceETV = Σ(v_i × synergy_i) / 6
PS = round(10 × (faceETV + passiveEV))
```

Качество не применяется повторно к уже вычисленным `v_i`. Нет отдельного ×MAGIC/×RARE. Базовый костяной кубик остаётся **55 PS**, тот же набор на Iron даёт **59 PS**.

### Пассивный EV — точные временные коэффициенты

Обозначения:

- `a(ID)` — значение аффикса, 0 при отсутствии.
- `E_A[f(v)] = Σ_{i с действием в A} f(v_i) / 6` — взвешенная по всем шести граням сумма, **не** среднее только выбранного действия.
- `p_A = число граней с действием в A / 6`.
- `μ = Σv_i / 6`.
- `rerollGain = Σ max(0, μ − v_i) / 6` — средний положительный выигрыш от замены плохой грани независимым броском.
- `flipGain = Σ max(0, v_opposite(i) − v_i) / 6`.

`passiveEV` — сумма:

| Аффикс                       | Вклад                                                                | Гипотеза модели                                               |
| ---------------------------- | -------------------------------------------------------------------- | ------------------------------------------------------------- |
| P6, шипы                     | `a(P6) × p_GUARD × 2/3`                                              | Шанс полезного щита/контакта 2/3                              |
| P8, пробитие щита STRIKE     | `0.5 × E_STRIKE[min(a(P8), 4, v)]`                                   | Щит в половине случаев, эталонный щит 4                       |
| S1, вампиризм                | `a(S1)/100 × E_{STRIKE,PIERCE}[v]`                                   | Номинальное лечение, без ограничения недостающим HP           |
| S2, дополнительные перебросы | `a(S2) × rerollGain / H`                                             | Дополнительные заряды распределены по шести ходам             |
| S3, начальный focus          | `min(3, a(S3)) × flipGain / H`                                       | Полезный flip из дополнительных начальных зарядов             |
| S4, яд                       | `a(S4) × 3 × p_PIERCE`                                               | Три полных тика, без моделирования обновления/ранней смерти   |
| S5, сохранение щита          | `a(S5)/100 × 0.5 × E_GUARD[v]`                                       | В среднем половина полученного щита остаётся                  |
| S6, эффективность стойки     | `0.5 × E_{STRIKE,GUARD,PIERCE}[ceil(v × a(S6)/100) − ceil(v × 0.5)]` | Половина подходящих случаев использует стойку; без S6 вклад 0 |
| S7, maxHP                    | `a(S7) / H`                                                          | Дополнительный запас HP распределён по шести ходам            |

Базовые возможности без аффиксов не получают дополнительного пассивного бонуса; это сохраняет исходную шкалу 55 PS. Отдельные свойства могут не повысить целое значение PS на конкретном наборе граней. Рост качества проверяется на сгенерированных наборах по всем целым значениям 0–20; это regression check модели, не доказательство игрового баланса.

Прежде чем использовать PS для рейдового HP/рейтинга, модель требует симуляций и калибровки. Её смена должна быть версионированной: пересчитать предметы, изменить contentVersion/квалификацию, не переписывать действующие боевые снимки задним числом.

## Ревизии, снимки и квалификация

- `RoomMember.inventoryRevision` увеличивается при equip, lock/unlock, craft, dismantle и settlement похода. Это отдельный счётчик от `MapRun.revision`. Даже нулевая terminal-выплата увеличивает inventoryRevision.
- `Die.contentVersion` увеличивается на **каждый успешный крафт**, включая идентичный случайный результат. Equip/lock не меняют содержимое и эту версию.
- Крафт очищает `lastVictoryAt` и `lastVictoryPowerScore`.
- Снимок на старте нового похода включает contentVersion. Победа обновляет квалификацию только при совпадении текущей версии предмета со снимком. Старые stage-2 снимки без поля читаются как версия 0.
- Победа над обычным/элитным врагом в новом тренировочном походе уже считается победным использованием; не обязательно ждать босса. Сам рейтинг ещё не реализован.

## HTTP, транзакция и retry

Все пути требуют подписанного Telegram-контекста, членства и общего лимита 5 запросов/с. `GET /api/inventory` возвращает `{ hub, activeRunDieId, policies, powerScoreModel }`. `policies` рассчитываются сервером для каждого предмета: equip, dismantle с выходом пыли и шесть craft options с ценой/причиной запрета/признаком разрушительности.

Каждый POST требует UUIDv4 `Idempotency-Key`, `dieId` и `expectedRevision` из `hub.player.inventoryRevision`:

| POST                       | Дополнительные поля                     |
| -------------------------- | --------------------------------------- |
| `/api/inventory/equip`     | Нет                                     |
| `/api/inventory/lock`      | `locked: boolean`                       |
| `/api/inventory/dismantle` | `confirmed: true`                       |
| `/api/workshop/craft`      | `sphere: SphereType`, `confirmed: true` |

Неизвестные поля/параметры запрещены. Сервер повторно проверяет ревизию, собственность, защиту, редкость, активный снимок и кошелёк под row lock. Подсказки UI не заменяют эти проверки.

Общий `memberCommand` берёт блокировку member, затем операция — die; создаёт запись idempotency **в той же транзакции**, что предмет/валюта. Namespace `inventory:v1` не совпадает с `game:v1`, но уникальность ключа общая на member. Один UUID нельзя переиспользовать между боем и крафтом. Ошибка любого шага откатывает все изменения. Неуспешная откатившаяся команда не сохраняет успешную запись replay.

Случайный крафт использует отдельный приватный seed `randomBytes(32)` и HMAC-домен `craft` с локальным счётчиком. Seed не возвращается/не хранится в браузере; результат успешной операции хранится как публичный JSON. Чтения и replay не вызывают RNG. Новая попытка после полного rollback может иметь новый seed, но предыдущий откатившийся результат клиент не видел.

Повтор успешного ключа в течение 24 часов возвращает **точно прежний** ответ, до проверки текущей ревизии. Другое тело — `409 IDEMPOTENCY_CONFLICT`. После TTL остаётся tombstone: `409 IDEMPOTENCY_EXPIRED`, а не повторный расход.

Ответ `{ inventory, result }`:

- CRAFT: исторические `before/after`, type, dieId, sphere;
- DISMANTLE: type, dieId, начисленная dust;
- EQUIP/LOCK: type, dieId.

На клиенте неизвестный результат/5xx/429 сохраняет **неизменные nonce/body**, блокируя новые мутации. Retry дополнительно читает `/api/inventory`, поскольку прежний cached response может быть старее действий другого устройства. Если POST подтверждён, а чтение упало, повтор списания не предлагается — только refresh. При 409 команда отклоняется; свежий GET не подставляет новую ревизию в старое подтверждение автоматически.

Подтверждение фиксирует копию кубика/цены/версии. Закрытие, Escape, Telegram Back не отправляют POST. После reload читается актуальный сохранённый инвентарь; nonce, initData и боевой/крафтовый RNG в persistent storage отсутствуют.

## Границы этого этапа

- Начальный комплект не меняется: один костяной кубик, Отливка 3 / Закалка 2 / Гранение 1, остальные сферы 0.
- Тренировка не даёт новый предмет/сферы. Нельзя проверить получение дополнительного кубика через production UI до реализации обычного дропа.
- Пыль за тренировку/распыление сохраняется; точечная огранка и другие траты пыли отложены.
- Full onboarding, обычная экономика, рейды, рейтинг и анонсы не выдаются за готовые.
- Browser preview — только отображение: мутации отключены, защищённые HTTP не вызываются, RNG отсутствует. E2E используют подмену SDK/HTTP; реальный Telegram smoke-test ещё нужен.
