# Архитектура: основание и тренировочный бой

Источник требований — патч v2.0. При расхождении с первым документом приоритет у v2.0. Текущая реализация включает основание и первый тренировочный игровой цикл, но не всю экспедиционную/крафтовую/рейдовую экономику.

## Доверие и путь запроса

```text
/game в группе
  → bot.getChatMember(сам бот): требуется administrator
  → Room.upsert(telegramChatId), случайный стабильный slug
  → обычная URL-кнопка t.me/bot/app?startapp=slug

Telegram.WebApp.initData (строка в памяти браузера)
  → Authorization: tma ...
  → ограниченный размер + отсутствие дублирующихся полей
  → HMAC-SHA256(WebAppData, botToken), затем HMAC(data_check_string)
  → timingSafeEqual, auth_date ≤ now + 30 s, возраст < 24 h
  → user + start_param только из проверенной строки
  → Room по подписанному slug, telegramChatId только из БД
  → getChatMember(chatId, signedUserId)
  → транзакция регистрации либо row-locked игровая операция
  → безопасный HubDTO / RunDTO без RNG-секретов
```

Для bot-token HMAC в `data_check_string` включены **все** поля, кроме `hash` (в том числе дополнительное `signature`). Это не алгоритм сторонней Ed25519-валидации, где правила исключения полей другие.

`restricted` без `is_member: true`, `left` и `kicked` не допускаются. Сетевые ошибки / отсутствие прав у бота — 503, а не разрешение входа.

### Кэш и лимиты

- In-memory LRU только **положительных** проверок: TTL 5 минут, 5 000 ключей. Хит не продлевает TTL.
- Параллельные cache miss одной пары `(chatId, userId)` объединяются в один вызов Bot API.
- Отказ и ошибка Telegram не кэшируются. Изменения членства могут вступать в силу с задержкой до 5 минут — осознанный компромисс MVP.
- Bot API timeout 5 секунд для авторизации.
- 5 запросов/с на **проверенный Telegram user ID**, общий для всех его комнат. Дополнительно 30 запросов/с на IP до HMAC.
- Непроверенные `user_id`, IP из `X-Forwarded-For`, `chat_id`, URL/query/startapp и `initDataUnsafe` не используются для выдачи доступа.
- Лимит и кэш локальны одному API-процессу. Redis не используется. Несколько API-реплик потребуют общих limiter/cache или эквивалентной защиты на gateway.

## Регистрация без повторной выдачи

В PostgreSQL одной транзакцией:

1. `pg_advisory_xact_lock(hashtextextended(roomId + telegramUserId, 0))`. Блокировка существует даже до появления `RoomMember`; снимается при commit/rollback. Коллизия 64-битного hash лишь сериализует несвязанные регистрации, не объединяет их профили.
2. Upsert общей Telegram-идентичности `User`.
3. Поиск `RoomMember` по `(roomId, userId)`.
4. Только если его нет: профиль → костяной кубик → шесть строк кошелька → `equippedDieId`.
5. Блокировка `RoomMember FOR UPDATE`, безопасное восстановление бодрости и сборка DTO.

Ошибка любого последующего шага откатывает весь комплект. Повторный session-запрос не сбрасывает баланс и не создаёт второй кубик. Это **естественная идемпотентность регистрации**, а не реализация будущего `Idempotency-Key` крафта.

## Решения по данным

В схеме исправлены пробелы образца v2:

- Один `User`, но отдельные `RoomMember` для каждого чата. Личные фрагменты — `RoomMember.sealFragments`, общий алтарь — `Room.sealFragments`.
- Единственный источник экипировки — `RoomMember.equippedDieId`, без конкурирующего `Die.isEquipped` в БД. DTO вычисляет этот флаг.
- Составной FK `(equippedDieId, member.id) → (Die.id, Die.ownerId)` запрещает чужую экипировку, даже при ошибке будущего сервиса.
- `Die.isLocked`, `isStarter`, `masterCrafted` сохранены. Разрушительных endpoints нет. Правила отказа от распыления стартового/заблокированного кубика должны также войти в будущий inventory service.
- `MapRun` имеет много `Battle`, а частичный индекс допускает один незавершённый бой. Это позволяет сохранять историю разных узлов, в отличие от `Battle.runId @unique`.
- `AWAITING_DECISION` требует зафиксированную грань 1–6. `battleSeed` и `stepIndex` используются серверным HMAC PRNG; intent, эффекты и грань сохраняются вместе с переходом FSM.
- По одному активному походу на профиль и активному рейду на комнату; по одному стартовому кубику на владельца.
- Неотрицательные валюты, пределы качества/ilvl/бодрости/HP, ровно шесть записей граней и максимум четыре аффикса — CHECK в миграции. Шесть различных граней, редкость, пул/тиры/значения и лимит 2+2 аффиксов дополнительно проверяет `combatDieSchema` при фиксации боевого снаряжения. Добавление/удаление вещей и дальнейший контроль ёмкости сумки относятся к будущему inventory service.
- `MapRun` хранит `revision`, неизменяемый `dieSnapshot`, посещённые узлы и результат settlement. Для новых походов CHECK связывает terminal status, `completedAt`, `settledLoot` и `lootSettledAt`. `Battle(runId, nodeId)` уникален; terminal state требует outcome.
- Для будущего рейтинга: `lastVictoryAt` и **снимок** `lastVictoryPowerScore`, а не бессрочный максимум PS на профиле. После каждой победы в тренировочном бою сохраняются время и PS из снимка похода. Так крафт после победы сам по себе не доказывает силу новой конфигурации; сам рейтинг ещё не реализован.
- Идемпотентность подготовлена как `(memberId, key)`, с `requestHash`, статусом, телом ответа и TTL. Один пользователь не может получить ответ другого по общему UUID. Игровые мутации уже сохраняют ответ и повторяют его транзакционно. Через 24 часа старые тела ответов сжимаются при следующей успешной мутации владельца, но ключи сохраняются как tombstone, чтобы не допустить повторного выполнения после TTL. Политика долгосрочного архивирования ещё нужна; крафта нет.
- `GameEvent` подготовлен как outbox: enum из трёх видов события, `dedupKey`, `sentAt`, attempts. Delivery worker, обработка 403 и ограничение анонсов шедевра раз в 12 часов относятся к этапу 4.
- Telegram ID — PostgreSQL `bigint`, даты — `timestamptz`. Внутренние ID — UUID. В публичных DTO нет `bigint`, токенов или seed.

Используйте миграции, не `prisma db push`: ручные CHECK и partial unique indexes составляют часть модели. Prisma Client 7 работает через pg adapter без query-engine binary. CLI миграций использует отдельный schema-engine.

## Бот и комнаты

- Бот отвечает на `/game`, `/start`, `/help`. Случайных рассылок нет.
- `/game` работает только в группе/супергруппе. Slug не содержит chat ID и не является секретом или доказательством членства.
- Повторный `/game` сохраняет slug. Коллизия нового slug обрабатывается ограниченным повтором.
- `migrate_to_chat_id` и `migrate_from_chat_id` обновляют ID той же комнаты. Профили, slug, кубики и валюты сохраняются.
- Если целевой chat ID уже занят другой комнатой, операция завершается ошибкой вместо разрушительного автоматического слияния.
- `my_chat_member` обновляет `canSendMessages`; при демоции до обычного участника учитываются общие права отправки сообщений чата.
- Long polling — один процесс. До `bot.start()` проверяется отсутствие настроенного webhook.

## Серверный игровой запрос

После HMAC, общего per-user limiter и membership:

1. По `(Room.id, signed Telegram user ID)` находится существующий `RoomMember`; игровые endpoints не регистрируют профили сами.
2. Транзакция берёт `RoomMember FOR UPDATE`. Регистрация/хаб используют ту же блокировку для балансов. В игровых мутациях порядок всегда **member → run → battle**.
3. Проверяется `(memberId, UUIDv4 key)`: hash нормализованного тела + типа операции, TTL, сохранённый успешный JSON. Проверка replay предшествует проверке текущей версии, чтобы повтор завершённого хода вернул его прежний результат.
4. Для новой команды проверяются владение run/battle, `IN_PROGRESS`, `expectedRevision`, достижимость узла и допустимость перехода FSM.
5. Чистое ядро получает состояние и, только если нужен бросок, результат серверного PRNG. Оно не читает часы/БД, не вызывает RNG и не меняет входные объекты.
6. Сохраняются состояние, RNG-counter, новая revision, добыча/settlement, победное использование кубика и **ответ идемпотентности в той же транзакции**. Ошибка на последнем шаге откатывает всё, включая кошелёк.

`SELECT FOR UPDATE` делает операции разных процессов безопасными для данных; тест с двумя экземплярами репозитория это проверяет. Это **не разрешение запускать несколько API-реплик** без общего rate limiter: ограничения запросов и membership cache по-прежнему рассчитаны на один процесс.

### RNG и восстановление

- `randomBytes(32)` генерирует отдельные секреты для карты и каждого боя. Seed остаётся в PostgreSQL.
- `HMAC-SHA256(seed, dicebound:v1:domain:step:retry)`, 32-битное слово и rejection sampling без modulo bias. Домены карты, выбора врага и броска разделены.
- `Battle.stepIndex` увеличивается только на успешный `ROLL`/`REROLL`, в одной транзакции с сохранением грани. Невалидная команда и rollback не продвигают последовательность.
- `GET /api/map/current` возвращает активный поход либо последний завершённый. Чтение/перезапуск процесса не генерирует новую карту, грань или intent.
- DTO собираются явной проекцией; `seed`, `battleSeed`, `stepIndex`, Telegram ID и ORM records в ответ не попадают.
- Новая миграция сохраняет совместимость с foundation-only строками без `nodeId`/`dieSnapshot`. Хаб их читает; боевой API не пытается продолжать такие вручную созданные старые записи (`UNSUPPORTED_RUN`). В этапе 1 API создания походов не было.

### Клиент и потери связи

Клиент не рассчитывает исход боя: отображает `options`, intent и результат сервера. Нет optimistic HP, локального броска или dev-login. UUID запроса — технический nonce, не источник боевой случайности.

Пока мутация выполняется, двойное нажатие блокируется. При неоднозначной сетевой ошибке/5xx либо 429 сохраняются исходные тело и ключ, другие действия недоступны. Успешный повтор дополнительно загружает актуальный поход, поскольку cached response может быть старее уже выполненных ходов другого устройства. `409` отклоняет команду и вызывает чтение, но никогда не повторяет её автоматически с новой revision.

Nonce/body и `initData` остаются только в памяти. После перезагрузки клиент читает сохранённый серверный FSM, а не повторяет команду с новым ключом. При смене сессии старые запросы не могут заменить новый профиль/поход: stores проверяют поколение сессии. Ошибка начального чтения блокирует начало новой тренировки до успешного refresh.

## Браузерный обзор не является серверным dev-login

`apps/web/src/lib/demo.ts` и `demo-run.ts` — изолированные UI fixtures с явной маркировкой. В примере боя все действия отключены; защищённые endpoints не вызываются. Сервер **не имеет** `DEMO_MODE`, тестового Bearer-токена или доверенного `user_id`.

Без Telegram SDK/initData показывается обзор. При наличии данных выполняется настоящий session-запрос. Ошибка входа остаётся ошибкой; переход в обзор возможен только явной кнопкой. Мастерская/рейды/рейтинг обозначены как будущие разделы. Боевой RNG не входит в браузерную сборку.

## Правила и оставшиеся вопросы

Разрешённые для прототипа неоднозначности flip/stance/poison/thorns/retention, таблицы баз/аффиксов, масштаб тренировки и порядок эффектов зафиксированы в [боевом контракте](combat.md) и тестах. Это явные выбранные соглашения, а не незаметное дополнение исходной спецификации.

Не решены следующие вопросы для следующих этапов:

1. **HP рейда и размерность PS.** PS уже равен `10 × ETV`, поэтому ожидаемый урон должен использовать `PS / 10`, а не PS. ETV содержит щит/лечение; коэффициент 0.65 требует калибровки, не трактовки PS как чистого DPS.
2. **Ровно 6 вылазок за 48 часов.** Три атаки на календарные UTC-сутки могут дать девять атак за рейд, пересекающий три даты. Нужен total-cap 6 либо два 24-часовых окна от призыва.
3. **Пассивный EV.** Боевые эффекты аффиксов реализованы; автоматический оценщик их вклада в PS пока нет. `calculatePowerScore` принимает bonuses/passive EV явно. Прежде чем открыть крафт/рейтинг, нужно согласовать веса и проверять snapshot PS.
4. **Сфера Переплавки** в наградах топа отсутствует среди шести сфер MVP. Скрытая седьмая валюта не добавлена.
5. **Полная экономика и onboarding.** Нормальный уровень/дроп, расход бодрости, inventory/crafting, обучение с гарантированным крафтом и финальное снятие tutorial-флага не входят в этот инкремент. Все будущие мутации ресурсов должны соблюдать тот же lock order и replay contract.
6. **Долгосрочное хранение.** Tombstone защищает nonce после 24 часов, но количество строк растёт. Нужна политика архивирования, не простое удаление по `expiresAt`, вновь разрешающее старый `START`.
