# Резервная копия базы в личных сообщениях

PostgreSQL остаётся рабочей базой. Бот периодически снимает её полный дамп и
присылает файлом в личные сообщения админа — копию видно в чате, её можно
скачать и восстановиться из неё.

Причина, по которой это не формальность: бесплатная база Render удаляется через
30 дней вместе с данными. Копия в чате — способ вернуть прогресс игроков.

## Включение

Задайте `BACKUP_CHAT_ID` — идентификатор личных сообщений админа:

```bash
BACKUP_CHAT_ID=123456789
BACKUP_INTERVAL_HOURS=6   # период, по умолчанию 6 часов
```

Узнать свой идентификатор: напишите боту любое сообщение и откройте
`https://api.telegram.org/bot<ТОКЕН>/getUpdates` — поле `chat.id` в ответе.

Без `BACKUP_CHAT_ID` копирование выключено: бот работает как обычно.

Снимок при старте не делается намеренно. Бесплатный инстанс Render засыпает и
просыпается, поэтому копия при каждом старте завалила бы чат одинаковыми
файлами. Первую копию снимите командой `/backup`.

## Команда /backup

Доступна только владельцу бота в личных сообщениях. В любом другом чате бот
отвечает отказом: полный дамп содержит данные всех игроков.

## Предел в 20 МБ

Bot API позволяет отправить документ до 50 МБ, но скачать обратно через
`getFile` — только до 20 МБ. Снимок больше 20 МБ восстановить через бота
невозможно, поэтому он **не отправляется**: вместо файла админ получает
предупреждение с фактическим размером и числом строк.

Отправить невосстановимую копию молча было бы хуже — она создаёт ложное чувство
защищённости. Если предел достигнут, базу нужно выгружать внешним способом.

## Восстановление

Скачайте файл из чата и выполните:

```bash
npm run build:server
DATABASE_URL=postgresql://... npm run db:restore -- <файл> --yes
```

Без `--yes` команда показывает содержимое снимка и завершается с кодом 1:
восстановление заменяет всё содержимое базы.

Восстановление намеренно не является HTTP-эндпоинтом. Полная перезапись базы по
запросу из интернета была бы дырой, а не функцией.

Восстановление идёт в одной транзакции, внешние ключи и триггеры не
отключаются. Повреждённый снимок откатывается целиком, а не записывает
несогласованные данные — это проверено тестом.

## Как устроен снимок

Формат — gzip-сжатый JSON с версией формата, временем снятия и числом строк.
В конверте указаны `formatVersion`, `createdAt`, `rowCount` и строки по
таблицам; снимок другой версии отклоняется, а не читается наугад.

Снимок делается в транзакции уровня `RepeatableRead`, поэтому все таблицы
относятся к одному моменту: в копию не попадёт участник без своей комнаты.

Таблицы обходятся в порядке внешних ключей. В схеме есть один цикл —
`RoomMember.equippedDieId` ссылается на `Die`, а `Die.ownerId` на
`RoomMember`, причём ограничение не откладываемое. Поэтому ссылка на
экипированный кубик восстанавливается отдельной фазой: сначала участник
создаётся с пустой ссылкой, затем загружаются кубики, затем ссылка
возвращается.

Типы приводятся явно: `JSON.stringify` падает на `BigInt`, а `Date`
превращается в строку без пометки о типе. `BIGINT` и `TIMESTAMPTZ` переживают
цикл без потери точности — это проверено отдельным тестом.

## Чего копия не покрывает

Это резервная копия, а не замена хранилища. Между снимками данные живут только
в PostgreSQL: если база погибнет, изменения после последнего снимка будут
потеряны. Период задаётся `BACKUP_INTERVAL_HOURS`.

Старые копии накапливаются в чате: бот не может удалять сообщения старше
48 часов. Это скорее полезно — получается история точек восстановления.

## Безопасность

Дамп содержит данные всех игроков: идентификаторы Telegram, имена, прогресс,
содержимое инвентаря. Он уходит только в личные сообщения, указанные в
`BACKUP_CHAT_ID`. Содержимое файла не пишется в логи, а `DATABASE_URL` в выводе
`db:restore` печатается с замаскированным паролем.
