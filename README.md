# Dicebound: Chat Raiders

Асинхронный roguelike для дружеских Telegram-чатов. Один чат — одна **Обитель**, отдельный герой и один активный боевой кубик.

**Готовы основание, серверный тренировочный бой, инвентарь с Мастерской, обучение, обычные экспедиции с расходом бодрости, серверный дроп предметов/сфер и точечная огранка Мастера за пыль. Это ещё не весь MVP.**

## Что уже работает

- npm-монорепозиторий: Fastify API, grammY-бот, React 18 / Vite / Tailwind / Zustand Mini App, общие типы, игровое ядро и Prisma.
- PostgreSQL-схема и четыре SQL-миграции с enum, FK, CHECK, триггером лимита сумки и частичными уникальными индексами.
- `/game` в группе создаёт комнату со стабильным `r_<nanoid(8)>` и отправляет **URL-кнопку**, не `web_app`.
- Проверка Telegram HMAC через `timingSafeEqual`, срока подписи и членства через `getChatMember`; ограниченный участник допускается только при `is_member = true`.
- Атомарная регистрация `(telegram_user_id, room_id)`, в том числе при параллельном первом входе.
- Стартовый костяной кубик с **55 PS**, 150 золота, 3 сферы Отливки, 2 Закалки и **1 Гранения**. Кошелёк не занимает слоты сумки.
- `POST /api/auth/session`, `GET /api/hub`, health checks, 5 запросов/с на подписанного Telegram-пользователя.
- Ленивое восстановление бодрости по UTC: +3 в сутки, максимум 6; без cron.
- Хаб, просмотр 12 слотов сумки, шести граней / противоположных пар и кошелька сфер. Мобильная навигация, клавиатурные диалоги и Telegram BackButton.
- Обработка миграции группы в супергруппу и изменения прав бота.
- Семь уровней тренировочных катакомб: ветвящийся DAG, обычные/элитные бои, сундуки, привалы и босс. **Бодрость не тратится**, награды — только небольшие суммы золота и пыли.
- Серверные броски с секретным 256-битным seed, сохранённой гранью и четырьмя решениями: разыграть, сменить стойку, перевернуть, перебросить. Шесть типов врагов и вычисление эффектов 15 аффиксов.
- Транзакционные действия: блокировки PostgreSQL, `expectedRevision`, UUIDv4 `Idempotency-Key`, восстановление после перезапуска, ровно одно начисление награды.
- Экран карты/боя с намерениями врага, подсказками действий, хроникой, подтверждением отступления и безопасным повтором при потере ответа.
- Экипировка, защита/снятие защиты и подтверждённое распыление в пыль; стартовый, защищённый, экипированный и используемый активным походом кубики нельзя распылить. SQL-триггер ограничивает сумку 12 предметами.
- Шесть сфер изменяют существующий кубик, сервер пересчитывает эффективные грани и PS. Подтверждение фиксирует предмет, цену и ревизию; результат показывает «до/после». Крафт и смена экипировки не меняют снимок текущего похода.
- Общая транзакционная идемпотентность боя/инвентаря, версия кошелька и версия содержимого предмета; старый ответ не откатывает ресурсы в UI, а победа старым снимком не подтверждает свежий крафт.

- Обучение из четырёх проверяемых шагов: настоящая победа в тренировке, разовая учебная сфера Отливки, любой успешный крафт и явное завершение. Прогресс сохраняется на сервере, прежние победы и крафты засчитываются миграцией.
- Обычные экспедиции 1–50 уровня за **1 бодрость**: сложность и снаряд фиксируются на старте, уровень открывается только победой.
- Серверный дроп золота, пыли, сфер и кубиков; при поражении или отступлении сохраняется 40% с округлением вниз.
- Найденные кубики ждут в **трофеях**: их нужно взять в сумку или распылить за пыль. Полная сумка не уничтожает предметы, повторный запрос не выдаёт второй предмет.

### Чего ещё нет

Реального smoke-теста Bot API и продуктового деплоя.

Новый игрок по-прежнему получает **один** стартовый кубик и сферы 3/2/1; остальное добывается в экспедициях. Endpoints не создают бесплатное снаряжение/валюту. Пыль сохраняется. Автооценка пассивного EV, диапазоны случайного гранения, выход распыления, шкала сложности и таблицы дропа реализованы как **явные временные правила**, не как откалиброванный финальный баланс.

Таблицы будущих систем подготовлены, но **наличие таблицы не означает готовый сервис**. Точные боевые соглашения и временные параметры тренировки описаны в [боевом контракте](docs/combat.md), формулы PS и операции с предметами — в [контракте Мастерской](docs/workshop.md), обучение, стоимость походов и таблицы дропа — в [контракте экспедиций](docs/expeditions.md); это не утверждение, что все спорные детали уже были однозначно заданы в v2.0.

В обычном браузере показывается явно обозначенный **обзор интерфейса** с тестовыми данными. В разделе «Походы» доступны карточка обучения, выбор уровня и фиксированный **пример боя только для просмотра**, без клиентского RNG. Мастерская и операции с инвентарём также доступны только для просмотра. Обзор не обращается к защищённому API, не сохраняет прогресс и не является обходом Telegram-авторизации. При ошибке настоящей Telegram-авторизации приложение показывает ошибку, а не подменяет профиль демонстрационным.

## Быстрый просмотр интерфейса

Нужны **Node.js 22.12+** (также поддерживается 20.19+) и **npm 11.6.2+**.

```bash
npm ci
npm run dev:web
```

Откройте `http://localhost:5173`. База данных и Telegram-токен для просмотра не нужны. Сервер слушает `0.0.0.0`; разрешены preview-хосты `*.e2b.app`. Шрифты включены локально, внешние CDN для обзора не нужны.

## Полный локальный запуск

### 1. Окружение и PostgreSQL 16

```bash
cp .env.example .env
# Отредактируйте .env локально: DATABASE_URL, BOT_TOKEN, APP_SHORT_NAME.
# Не отправляйте токен в чат и не добавляйте .env в Git.

npm ci
docker compose up -d --wait db
npm run db:generate
npm run db:migrate
npm run dev
```

`compose.yaml` поднимает **только локальную БД**, привязанную к `127.0.0.1:5432`. Для production используйте отдельные учётные данные, TLS, резервные копии и закрытую сеть. Пароль из примера — исключительно для разработки.

`npm run dev` собирает общие пакеты и запускает API, бота и web. После изменения общих серверных пакетов перезапустите эту команду. Отдельно доступны:

```bash
npm run dev:api       # :3001, с предварительной сборкой общих пакетов
npm run dev:bot       # long polling
npm run dev:web       # :5173, без БД и токена
```

### 2. Настройка Telegram

1. Создайте бота у BotFather. Сохраните его токен **только в локальном `.env` / секретах хостинга**.
2. Создайте Mini App через `/newapp`, задайте HTTPS URL фронтенда и short name. Этот short name укажите в `APP_SHORT_NAME`. Имя бота берётся из `getMe`, а не из клиентского запроса.
3. Веб-страница и `/api` должны быть доступны через **один HTTPS-origin**. В разработке Vite проксирует `/api` на `API_PROXY_TARGET`. Браузер никогда не обращается к `localhost` другого сервиса.
4. Добавьте бота в тестовую группу и назначьте администратором. Это необходимо для гарантированной проверки других участников через `getChatMember`; права удаления сообщений/блокировки людей не требуются.
5. Отправьте `/game`. Ссылка будет вида `https://t.me/<bot>/<app>?startapp=r_abcdefgh`.
6. Откройте кнопку внутри Telegram: сервер проверит подписанный `start_param`, членство и выдаст стартовый комплект.
7. Перейдите в «Походы» → «Начать тренировку». Закройте и откройте Mini App во время выбора действия: та же грань должна восстановиться с сервера.
8. В «Мастерской» выберите стартовый кубик и Отливку, Закалку либо Гранение. Цена — одна соответствующая сфера; подтверждайте только после чтения предупреждения. После reload сохранятся новый предмет и остаток валюты, а текущий поход продолжится со старым снимком.

Не запускайте два polling-процесса для одного токена. Бот отказывается стартовать при уже настроенном webhook, чтобы не переключить существующий deployment на polling. Для ручной проверки Telegram нужен доступ сервера к `api.telegram.org` и браузера к официальному SDK на `telegram.org`.

### 3. Сборка и deployment

```bash
npm run build
npm run start -w @dicebound/api
# В отдельном процессе:
npm run start -w @dicebound/bot
```

Статические файлы — `apps/web/dist`. На HTTPS reverse proxy направьте `/api/*` в API на `3001`, остальные запросы — к статике (SPA fallback на `index.html`). Не используйте Vite dev server для production. Native Telegram WebView и web.telegram.org должны иметь возможность открыть страницу; не устанавливайте `X-Frame-Options: DENY` для Mini App.

API не доверяет произвольному `X-Forwarded-For`. За reverse proxy его дополнительный IP-лимит будет общим для адреса прокси; при масштабировании задайте доверенные адреса прокси явно, не включайте безусловное `trustProxy: true`.

## API этого этапа

| Метод | Путь                         | Назначение / тело JSON                                                          |
| ----- | ---------------------------- | ------------------------------------------------------------------------------- |
| POST  | `/api/auth/session`          | Вход, создание/загрузка профиля; `{}`                                           |
| GET   | `/api/hub`                   | Баланс, инвентарь, бодрость, summary похода/рейда                               |
| GET   | `/api/raid`                  | Алтарь печати, рейд, открытый удар, права действий                              |
| GET   | `/api/leaderboard`           | Зал славы Обители за семь дней                                                  |
| POST  | `/api/raid/contribute`       | Внести личные фрагменты печати в алтарь                                         |
| POST  | `/api/raid/summon`           | Призвать рейд Обители                                                           |
| POST  | `/api/raid/attack`           | Потратить рог и получить серверный бросок                                       |
| POST  | `/api/raid/decide`           | Разыграть удар: `DIRECT` / `SHIFT` / `REROLL`                                   |
| GET   | `/api/map/current`           | Активный или последний завершённый поход; `{ run: null }`, если походов ещё нет |
| POST  | `/api/map/start`             | Новая бесплатная тренировка; `{}`                                               |
| POST  | `/api/map/step`              | `{ runId, expectedRevision, nodeId }`                                           |
| POST  | `/api/map/retreat`           | `{ runId, expectedRevision }`                                                   |
| POST  | `/api/battle/roll`           | `{ runId, expectedRevision, battleId }`                                         |
| POST  | `/api/battle/decision`       | `{ runId, expectedRevision, battleId, action }`                                 |
| GET   | `/api/inventory`             | Инвентарь, баланс, активный предмет похода, разрешения на действия              |
| POST  | `/api/inventory/equip`       | `{ dieId, expectedRevision }`                                                   |
| POST  | `/api/inventory/lock`        | `{ dieId, expectedRevision, locked }`                                           |
| POST  | `/api/inventory/dismantle`   | `{ dieId, expectedRevision, confirmed: true }`                                  |
| POST  | `/api/workshop/craft`        | `{ dieId, expectedRevision, sphere, confirmed: true }`                          |
| POST  | `/api/workshop/master-facet` | `{ dieId, expectedRevision, face, action, confirmed: true }`                    |
| GET   | `/health/live`               | Жив ли процесс                                                                  |
| GET   | `/health/ready`              | Доступен ли PostgreSQL                                                          |

`action`: `DIRECT`, `SHIFT`, `FLIP` или `REROLL`. Мутации карты/боя возвращают `{ run: RunDTO }`; `options` уже рассчитаны сервером. Отдельный `commit` не нужен: **flip завершает ход**, а **reroll остаётся в выборе действия**.

Каждый `POST /api/map/*`, `/api/battle/*`, `/api/inventory/*` и `/api/workshop/*` требует заголовок **`Idempotency-Key: <UUIDv4>`**. Новый ключ создаётся один раз на намерение игрока; после timeout/5xx/429 повторяются **тот же ключ и неизменное тело**. До завершения повтора другие действия заблокированы. Повтор успешной команды в течение 24 часов возвращает сохранённый JSON, даже если поход уже продвинулся; после повтора клиент запрашивает `/api/map/current` либо `/api/inventory`. Изменённое тело с прежним ключом — `409 IDEMPOTENCY_CONFLICT`, просроченный ключ — `409 IDEMPOTENCY_EXPIRED`, не повторное выполнение.

`runId`/`battleId` не дают доступа сами по себе: сервер проверяет владельца в подписанном контексте чата. Для мутаций существующего похода обязателен целочисленный `expectedRevision` из последнего ответа. Устаревшая версия — `409 STALE_STATE`; клиент загружает актуальный поход, не повторяя старый ход с новой версией. Неизвестные поля, в том числе `face`, `seed`, `userId`, `chatId` и выбор режима наград, отклоняются.

Мутации инвентаря возвращают `{ inventory: InventoryDTO, result }`. `expectedRevision` здесь берётся из `hub.player.inventoryRevision`, **не из похода**. Ответ включает серверные разрешения и причины запрета; `result` крафта содержит исторические `before/after`, распыления — количество пыли. Конфликт — `409 STALE_INVENTORY`; нужно обновить данные и подтвердить новое намерение, а не молча подставлять новую версию. Все шесть `sphere` перечислены в `shared-types`; выбор грани/аффикса/значения клиентом запрещён.

Игровые запросы требуют `Authorization: tma <Telegram.WebApp.initData>`. Тело `POST /api/auth/session` — `{}`. `user_id`, `chat_id`, slug из URL браузера и `initDataUnsafe` не используются как источник идентичности.

«Session» здесь — операция инициализации, **не новый JWT**: каждый следующий запрос повторно проверяет `initData`. Срок действия — до 24 часов; после истечения нужно заново открыть Mini App через `/game`. `initData` остаётся только в памяти браузера, не попадает в storage или логи.

```bash
# INIT_DATA задаётся локально из собственного тестового запуска Telegram.
curl http://localhost:3001/api/auth/session \
  -H "Authorization: tma $INIT_DATA" \
  -H 'Content-Type: application/json' \
  -d '{}'
```

Ошибки имеют единый формат `{ "error": { "code", "message", "requestId" } }`. Ответы с профилем не кэшируются. Seed, Telegram ID и полные ORM-записи не выдаются клиенту.

## Проверки

```bash
npm run db:generate
npm run db:validate
npm run typecheck
npm test                     # unit + HTTP + mock Bot API
npm run format:check
npm run build
npm audit
```

Интеграционные тесты требуют отдельной PostgreSQL-базы с именем, заканчивающимся на `_test`. Они создают собственную случайную схему, применяют **реальный SQL всех миграций по порядку**, затем удаляют только эту схему.

```bash
# Например, для локального compose (создать один раз):
docker compose exec db createdb -U dicebound dicebound_test
TEST_DATABASE_URL='postgresql://dicebound:dicebound@localhost:5432/dicebound_test' \
  npm run test:integration
```

Проверяются: 20 параллельных регистраций и стартов; повтор/гонка roll и decision; сохранённая грань при восстановлении сервиса; чужие run/battle; неизменный снимок кубика; rollback RNG/HP/награды при ошибке записи ответа; победа/поражение/отступление; TTL ключей; обе SQL-миграции, FK/CHECK/partial indexes; HTTP → авторизация → настоящий PostgreSQL.

```bash
npx playwright install --with-deps chromium
npm run test:e2e              # desktop + mobile; Telegram SDK/API подменяются в UI-тестах
```

E2E проверяют навигацию, грани/сферы, карту и бой, крафт и «до/после», экипировку/защиту/распыление, отмену через Escape и Telegram BackButton, потерю ответа и повтор с тем же nonce, конфликты версий, ошибки чтения, кошелёк и reload, отсутствие API в обзоре и горизонтального overflow на ширинах 320–1440 px. Это **не** проверка реального Telegram-клиента. Для уже установленного Chromium можно задать `PLAYWRIGHT_CHROMIUM_EXECUTABLE_PATH`.

CI: `.github/workflows/ci.yml` — PostgreSQL 16, миграции, TypeScript, unit/integration, сборка и Chromium E2E.

## Структура

```text
apps/
  api/                 Fastify, Telegram HMAC, membership cache, безопасные DTO
  bot/                 grammY, /game /start /help, миграция чата, права бота
  web/                 React Mini App и отдельный UI-only обзор
packages/
  shared-types/        Публичные контракты без серверных секретов
  game-core/           Чистый FSM боя, шесть сфер, аффиксы, враги, DAG, награды, ETV/PS
  db/                  Prisma 7, pg adapter, репозитории, schema и SQL-миграции
tests/                 Fixtures и Playwright
```

> `prisma migrate` требует нативный schema-engine. При первой установке Prisma загружает его с `binaries.prisma.sh`; в среде с ограниченным egress этот домен может быть недоступен. Это не причина заменять PostgreSQL mock-данными или пропускать миграции в production. Локальные интеграционные тесты исполняют SQL непосредственно на PostgreSQL 16; CI дополнительно запускает нативный `migrate deploy` и полный `npm run build`. Ручной Telegram smoke-test требует окружения с доступом к Bot API и официальному SDK и пока не выполнен.
